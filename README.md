# csqtt-openwrt

Сборка пакетов [CSQTT](https://github.com/amurcanov/csqtt) для OpenWrt в GitHub Actions — **из открытых исходников**:

| Пакет | Что внутри |
|---|---|
| `csqtt` | служба `csqtt` (обёртка из `wrapper/`) + ядро `csqtt-core` (upstream `client`), init-скрипт, шаблон UCI |
| `luci-app-csqtt` | панель LuCI: статус, профили, настройки, CAPTCHA, журнал |
| `luci-i18n-csqtt-ru` | русский перевод |

Форматы: `.ipk` для OpenWrt 24.10 и `.apk` для 25.12. Архитектуры: `x86_64`, `aarch64_cortex-a53` (обязательные),
`arm_cortex-a7_neon-vfpv4` и `mipsel_24kc` (**экспериментальные**, см. ниже).

## Как это устроено

```
LuCI ──ubus/rpcd──▶ /usr/bin/csqtt (CLI: status, doctor, profile, --validate-vk-hashes)
                         │
procd ─▶ csqtt run ──────┤  читает /etc/config/csqtt, держит TUN csqtt0, пул профилей
   ▲ SIGHUP = reload     │  пишет /var/run/csqtt/status.json, журнал /var/log/csqtt.log
                         ├─▶ csqtt-core (upstream) ── stdin/stdout: события, STOP, CAPTCHA_RESULT
                         │        ▲ дескриптор TUN через абстрактный Unix-сокет (SCM_RIGHTS)
                         └─▶ CAPTCHA-помощник: API 127.0.0.1:8443 (для LuCI)
                                               страница решения LAN:8444 (для браузера)
```

* **Interface-only:** служба создаёт `csqtt0`, но не ставит маршруты, правила, firewall, NAT и DNS.
  Трафик в туннель направляете вы (например, `interface-name: csqtt0` в mihomo).
* **Пул профилей:** `selection_mode=priority` — берётся включённый профиль с **наименьшим** `priority`;
  при сбое (выход ядра, фатальная ошибка, таймаут, нет воркеров, провал пробы доступа) — failover на следующий,
  у сбойного cooldown. `failback` возвращает на лучший профиль после `failback_stable_time`.
  `selection_mode=manual` — только `active_profile`.
* **Адрес `csqtt0`:** при пустом `tun_address` на интерфейс назначается адрес, выданный сервером (`TUNCONF`, `/32`), как у
  Android-клиента; маршруты не добавляются. Без адреса привязанные к интерфейсу процессы (Mihomo `interface-name: csqtt0`)
  не получили бы source-адрес. Явный `tun_address` (CIDR) имеет приоритет. Адрес и DNS сервера видны в `csqtt status --json`
  (`tunnel.client_ip`, `tunnel.dns`) и в журнале.
* **Проверка доступа:** `health_target` (`host:port`, TCP через `csqtt0`) участвует в failover. Если он не задан, выполняется
  информационная проверка по умолчанию — один DNS-запрос к DNS, выданному сервером, через туннель (первый сразу после подключения,
  далее не чаще раза в 30 с, около 100 байт на запрос); её сбой **failover не вызывает**. Отключить: `option health_mode 'process'`.
* **Правка конфига** (профиль изменён/включён заново) сбрасывает cooldown этого профиля.

## Патчи к ядру

`patches/core-musl-udp-batch.patch` — минимальная правка `udp_batch.rs` ядра v2.1.9 для сборки под musl
(новые привязки `libc` меняют тип `flags` у `recvmmsg`/`sendmmsg` и закрывают поля `msghdr`). Применяется в CI
автоматически; если upstream исправит это сам, шаг это заметит и пропустит патч. `patches/core-mips32-atomic64.py` — только для mipsel: на mips32 нет `AtomicU64`/`AtomicI64`, скрипт подменяет их на
`portable-atomic` (на этой цели 64-битные счётчики станут чуть медленнее — реализация на блокировке). Для другой версии ядра патч может
не примениться — тогда CI выдаст предупреждение (`::warning::`), и его нужно будет обновить.

## Подключение репозитория

1. Создайте репозиторий и залейте содержимое этой папки в `main`.
2. *Settings → Actions → General → Workflow permissions* → **Read and write permissions** (нужно для публикации релизов).
3. Запустите *Actions → Build CSQTT OpenWrt → Run workflow* (галка «Тестовая сборка» — без публикации).
4. Релизы: `v<версия ядра>-r<PKG_RELEASE>` (пакет `csqtt`) и `luci-v<версия>-r<N>` (панель и перевод).

**Выпуск новой версии.** Новый релиз ядра upstream подхватывается автоматически (cron по пятницам).
Изменили `wrapper/`, init-скрипт или шаблон — увеличьте `PKG_RELEASE` в `csqtt/Makefile`.
Изменили файлы панели — увеличьте `PKG_VERSION`/`PKG_RELEASE` в `luci-app-csqtt/Makefile`.

Параметры ручного запуска (*Run workflow*): `test_build` — без публикации релиза; `core_ref` — другая версия ядра
(например, `v2.1.5`); `upx` — сжать ядро UPX на **всех** архитектурах (обёртка `csqtt` не сжимается: LuCI запускает её каждые несколько секунд) (вдвое меньше на флеше, но программа
распаковывается в память при запуске). В автоматических запусках (push, расписание) UPX не применяется. На mt7621 сжатые бинарники падали с `Illegal instruction` (причина выясняется).

## Установка на роутер

```sh
# 24.10 (ipk)             # 25.12 (apk, неподписанные пакеты)
opkg install ./csqtt-*.ipk ./luci-app-csqtt-*.ipk ./luci-i18n-csqtt-ru-*.ipk
apk add --allow-untrusted ./csqtt-*.apk ./luci-app-csqtt-*.apk ./luci-i18n-csqtt-ru-*.apk

csqtt profile import 'csqtt://connect?v=2&host=…&peer=…&password=…&hashes=a+b' --commit --activate
uci set csqtt.main.enabled=1 && uci commit csqtt
/etc/init.d/csqtt restart ; csqtt status ; csqtt doctor
```

`csqtt profile import` без `--commit` — пробный прогон. Секреты в выводе не печатаются.

## Новые опции UCI (`config csqtt 'main'`)

| Опция | По умолчанию | Назначение |
|---|---|---|
| `helper_bind` | LAN-адрес (`br-lan`) | адрес, на котором слушает **страница решения CAPTCHA** |
| `helper_host` | авто | хост в ссылке на решение (если роутер открывают по другому имени/IP) |
| `helper_solve_port` | `helper-port + 1` (8444) | порт страницы решения |

Остальные опции — как в шаблоне `/etc/config/csqtt`.

## CAPTCHA

Ядро само решает капчу автоматически (Rust v2). Если не вышло, оно просит ручное решение. В панели *CSQTT → CAPTCHA*
появляется задача; кнопка **Solve** показывает ссылку и QR. Откройте её в браузере **из локальной сети** — роутер
проксирует страницу VK (только домены `vk.com`, `vk.ru`, `ok.ru`, `okcdn.ru`), перехватывает ответ
`captchaNotRobot.check` (как делает Android-клиент) и передаёт `success_token` ядру.
Ссылка одноразовая, живёт столько же, сколько ожидает ядро (60 с для `manual`, 120 с для `wv`).
Режим `auto` (скрытый WebView) на роутере недоступен — ядро переходит к следующему шагу своей цепочки.

## Что проверено, а что нет

**Проверено (в песочнице разработки):**
* 23 unit-теста: разбор и правка UCI, ссылки `csqtt://`, протокол ядра, аргументы ядра, прокси-подмена ссылок, API помощника.
* Сквозной тест `tests/integration.py` на **настоящем TUN** с поддельным ядром того же внешнего контракта:
  создание `csqtt0` и MTU, передача дескриптора, выбор по приоритету, failover со сбоем аутентификации,
  ручной выбор, весь путь CAPTCHA (запрос ядра → challenge → ссылка → токен → `CAPTCHA_RESULT` ядру),
  `doctor`, `--validate-vk-hashes`, экспорт профиля, корректная остановка. Он же запускается в CI (job `test`).
* HTTPS-клиент прокси на реальном TLS-соединении.

**НЕ проверено — проверьте сами:**
* Сборка **настоящего** ядра (нужен Rust ≥ 1.97.1) и кросс-сборка через `cargo-zigbuild`.
* Сборка пакетов в OpenWrt SDK (Makefile и workflow написаны по стандартным шаблонам, но SDK в разработке не запускался), формат `.apk`.
* Установка на реальный роутер и туннель до реального сервера через VK/TURN.
* **Прокси CAPTCHA против живого VK.** Механизм повторяет Android-клиент, но VK может менять страницу; подмена ссылок
  и перехват сделаны «по максимуму» и могут потребовать доработки. Основная часть капч решается автоматически ядром без помощника.
* **mipsel**: статический PIE (`ET_DYN`) на mips32 с musl даёт `TEXTREL` и падает при старте (`Illegal instruction`/`SIGSEGV`) —
  найдено на реальном mt7621 и воспроизведено в эмуляторе. Для mipsel бинарники собираются без PIE
  (`-C relocation-model=static`), а CI запускает собранные файлы под `qemu-user` (смоук-тест) для всех архитектур.
  Это исправление проверено на обёртке (сборка и запуск в эмуляторе), **на самом ядре — нет**: сборка ядра у меня не запускалась.
* **mipsel (прочее)**: в Rust это Tier 3 (nightly + `-Zbuild-std`), у upstream такой цели нет — сборка может не получиться
  (jobs помечены `continue-on-error`). Отсутствие 64-битных атомиков на mips32 может сломать ядро. Это же касается armv7.
  Релиз публикуется, только если собрались обязательные `x86_64` и `aarch64`.
* Опция `dns` («Tunnel DNS» в панели) обёрткой пока **не используется**: я не знаю, как её применяет оригинал в режиме
  interface-only, а в ядре upstream флага для неё нет.
* Совместимость поведения обёртки с оригиналом автора проверялась по потребителям (LuCI/init), а не по его коду.

## Безопасность

* Пароль профиля передаётся ядру аргументом командной строки (как в upstream), он виден в `/proc/<pid>/cmdline`
  пользователям с доступом к процессам роутера. Конфиг хранится с правами `0600`.
* API помощника слушает только `127.0.0.1`. Страница решения доступна только по случайной ссылке (128 бит) и только в LAN
  (по умолчанию — `br-lan`); не пробрасывайте порт 8444 наружу.
* Прокси CAPTCHA ходит строго на allowlist доменов VK/OK; чужие хосты получают 403.
